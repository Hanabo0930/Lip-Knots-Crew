# 従来案件の作成・複製と再送

管理者の新規作成・複製は、応答を受け取れなかった場合にも同じ操作IDを使って結果を確認する。受信案件の既存mailIntake契約は変更しない。

## 要求と受領記録

createAdminJobGroup / duplicateAdminJob は、nativeCreation の中に operationId（UUID）、expectedCompanyId、expectedActorUid、action（create / cancel）、input を渡す。外側・内側の混在フィールドは拒否する。旧APIが操作IDを無視して作成しないよう、旧版で必要な平坦フィールドは付けず、旧形式へのフォールバックもしない。画面とAPIは同じ版へ移行する。

nativeJobCreationReceipts は会社と操作IDから求めるSHA-256のキーを持つ。担当者・処理種別・入力の正規JSONハッシュを照合し、案件、グループ、必要な行作成キュー、監査、受領記録を一つのFirestore transactionでcreateする。重複要求は保存済み案件の会社・グループ・caseId・受領記録IDを再照合し、最初の作成結果を返す。後から変わった担当・取消状態は書き戻さない。受領記録が壊れている、または案件が失われた場合は再作成せず確認を求める。

cancelは案件そのものの取消ではない。未確定の依頼に取消済み記録を残して遅れて届く同じ依頼を閉じ、すでに作成済みならその結果を返す。作成と取消は同じ受領記録を読み書きして競合を解決する。

## 画面

送信前に会社・ログイン別のlocalStorageへ入力と操作IDを保存する。保存不能・破損・Web Locks非対応では送信しない。未確認の依頼がある間は新しい作成を開始しない。確認パネルから同じ依頼を再送でき、再読込しても依頼を復元する。取消ボタンは確認ダイアログ後にサーバーへ照会する。

複数タブは同じ保存キーのWeb Lockを共有する。サーバーでも同じ操作IDを収束させる。ログイン・会社の変更時は元の依頼を保持し、異なるログインで送信・消去・古い結果表示をしない。受領記録の応答を照合できた場合だけ、自分の操作IDの保存依頼を消す。

同じ内容の別の操作IDは別の作成として扱う。端末保存を手動消去した場合や別の端末で新しい依頼を作った場合の意味的な重複排除は、この契約に含まない。受領記録へTTLや自動削除を設定しない。既存の平坦要求には再送保証を追加していない。

## 検証と移行条件

- 実SDK・隔離Firestore 39条件：同時再送、応答喪失、取消競合、会社・担当・入力の境界、保存済み案件の照合、監査失敗、複製元の変更を確認。
- 画面処理27条件と実ブラウザー6シナリオ：端末保存、再読込、複数タブ、会社切替、応答不一致、320/390/1280px表示を確認。API・認証境界は合成で外部通信0。
- 正式CIはnative-creation-retry隔離スイート、画面処理・ブラウザー試験、ソースガード変異試験を実行する。

この変更はFunctionsやworkerの実配備、原本追加、実業務API呼出、受付・転送・通知停止解除、Rules/IAM/Live変更を実行しない。作成・複製・取込の同版移行と、旧workerへの到着制御・実行終了確認は引き続き必要。原本追加が未設定なら下書き保存し、設定済みでも検算完了までは公開しない。
