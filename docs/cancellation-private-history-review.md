# 取消履歴を非公開にするための変更案（未承認・未反映）

現行の `jobs` 読取Rulesは、担当スタッフIDが一致すれば取消済みでも本人の読取を許可する。通常画面と応募APIから外しても、直接読取の権限は残る。画面非表示だけで非公開完了とは判定しない。

## 最小の案

既存の会社境界・管理者の読取は維持し、スタッフ向け `jobs` 読取条件の全体へ次の取消除外を加える。

- `status` が `cancelled` の案件はスタッフへ許可しない。
- `cancelled` が true の案件もスタッフへ許可しない。既存の古い文書でこのフィールドが欠ける場合を安全に扱う。
- 通常の募集・担当本人の確定案件・既存管理者のアクセスには既存条件を使用する。権限を追加・拡張しない。

取消された案件の担当ID・案件ID・Source照合証跡は変更しないため、Source取消ACK、勤務枠解放、履歴保持、管理者の年間依頼数照合の根拠を残せる。スタッフからの取消後の直接取得はpermission-deniedになるため、通常一覧・応募一覧・保存キャッシュの更新時は取消を取り除き、過去のキャッシュを新しい確定表示として復元しないことも検証する。Rulesはフィルターではないため、一覧クエリ全体が拒否されないよう、実際のスタッフ取得クエリとの組合せを隔離エミュレータで確認する必要がある。管理者の取消履歴は既存管理画面からのみ扱う。

## 実行前の確認範囲

1. 管理者だけが取消履歴と年間依頼数を取得できること。
2. 同じ会社の本人・他スタッフ・別会社・未認証の取消読取拒否。
3. 通常案件の取得・応募・確定・月間表示・ページングを壊さないこと。
4. 取消イベントの通常一覧・応募候補・通知・古いキャッシュからの情報露出が残らないこと。
5. 配備対象、既存Rules退避、復元手順、正確なコードと検証証跡を示すこと。

このファイルは検討案であり、`firestore.rules` 自体は編集・配備していない。本人の7条件の指示を、新しいRules／IAM／本番／GAS操作の承認とは扱わない。独立した非公開アーカイブ＋公開文書の無担当化も代案だが、現行の担当IDを使う取消ACK・再取込・勤務枠・復元の広範な変更が必要なため、権限除外より小さい修正とは言えない。
