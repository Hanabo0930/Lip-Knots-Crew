# 経費画面の読込・保存・通信失敗の整合

案件Aの読込中にBへ切り替えた場合の逆順応答、読込失敗後の旧金額保存、未読込保存、ログイン切替、対象不一致応答、二重クリック、保存中の案件切替、結果不明時の即再送を合成データで再現。初期14ケースは全件失敗し、修正後は追加6ケースを含む20ケースが成功した。

読込世代とログインユーザーを照合し、最新の対象だけを表示する。切替時は旧入力を消して未読込に戻し、読込に成功するまで入力/保存を無効にする。送信中は同期的な受付ロックで保存と確認完了の重複操作を防ぐ。別案件/別ログインへ変わった後に届く結果は表示しない。ログイン変更時も経費状態を初期化する。

通信エラーなど結果が不明な場合は入力値を画面に残し、再読込するまで再送しない。確認完了の成功後も再読込を必要とする。受付後に書込状況一覧の更新だけが失敗した場合は「受付済み」と案内し、送信失敗と混同しない。

実行：`node scripts/test-admin-expense-recovery.mjs`。実際のApp.tsxハンドラーを変換し、APIの応答順序・失敗・認証変更を合成境界で挿入する。実APIは呼ばない。`node scripts/test-admin-workspace.mjs --browser`では外部通信を拒否したローカルデモで、390/1280pxの管理画面、経費読込→一時保存→確認取消→完了承諾→再読込と操作可否を検証する。

初回の設定ありビルドでentryが359029bytesとなり350KiB上限を超えたため、経費表示をAdminExpensePanelへ分離し必要時に読み込む。制限は変更せず、設定ありentry349.4KiB/raw・102.0KiB/gzipを確認した。総通信量や実端末速度が同じ割合で改善するという測定ではない。

現行サーバーの既存API/応答を使用し、新API配備を前提にしない。複数端末/複数管理者の競合、サーバー側の受付IDによる重複排除、画面表示から保存までの版照合は未実装。再読込だけで結果不明時の重複可能性がなくなるとは扱わない。デモ保存は既存どおり表示上の模擬動作で、永続化しない。
