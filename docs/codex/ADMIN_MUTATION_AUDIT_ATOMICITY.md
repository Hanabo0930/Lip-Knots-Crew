# 公開・編集と監査の同時確定

公開状態の変更と管理者編集は、案件のtransactionが成功した後に監査を別保存していました。監査保存が拒否されると、画面へエラーを返しても案件の状態や住所・版番号は変わっていました。実SDK/隔離Firestoreで公開stopと住所編集の2条件を再現しました。

両APIの監査createを案件と同じtransaction内へ移し、成功・拒否を一緒に確定します。監査は既存IDを上書きせず、担当や原本を再照合する既存の読取順序を維持します。返却する結果と監査のdetail形式は変えません。

正式試験は、受信から作成・原本照合まで通した案件を使う6条件です。公開/アプリ内住所編集/原本書戻しを伴う店舗編集について、正常保存と監査拒否を実SDKで検証します。拒否時は案件・グループ・勤務枠・書戻し依頼・監査の内容が変わらないこと、成功時は対応する監査1件と必要な書戻し依頼だけが保存されることを確認します。原本操作は合成Sheetsのみです。

認証ソース検査には、監査が同じtxを使い結果return前に存在することを追加し、別batch・別会社・上書きへ改変した場合の拒否も確認します。既存の模擬DBはtransaction.createを記録し、実行をやり直した試行の監査を保存しない扱いに揃えます。

この変更は監査だけが失敗する部分保存を防ぎます。commit自体の応答喪失や、別API呼出を同一操作へ収束させる契約は別の問題です。実worker配備、実原本、実業務データ、実送受信、停止解除は含みません。
