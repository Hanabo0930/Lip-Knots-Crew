# 案件作成・原本照合・公開の連結

従来の管理者作成/複製はランダムなFirestore文書IDを使い、原本読取は固定caseIdから別IDを計算していました。そのため作成した行を再取込すると、同じcaseIdの案件が2件になりました。新規管理者作成と複製も、受信案件と同じ固定caseIdによるID規則に揃えます。従来の作成APIに操作IDの再送保証を追加する変更ではありません。

読取同期のトランザクションは、同じ会社・同じ管理者caseIdに別の既存文書があれば停止し、その文書を移動/削除/統合しません。旧ランダムIDの案件と、すでに複数文書へ分かれた案件の解消は別途の移行判断が必要です。この保護は既存データを自動修復するものではありません。以前の25件単位の保存は維持し、別chunkの保存まで原子的にするものではありません。

同じ案件へ取り込めるようになると、原本の担当欄が空白であることを理由に、管理者が保存した下書きを公開してしまう経路も確認できました。管理者作成案件の下書き・募集停止・予約公開は、原本の空欄を読み直しても保持します。公開済み案件は公開を維持し、担当/取消の既存判定は継続します。

`test-local-creation-journey.mjs` は、実SDKと隔離Firestore、実API/worker、合成メール/Sheetsで15条件を確認します。合成表はworkerが発行したinsertDimension/updateCellsを適用し、同じ表を実読取同期へ返します。

- 受信→解析→案件作成→行追加→原本読取→確認版付き公開。人数で分割した候補2件の一括公開も確認。原本照合前は公開不可、イベント/受信の再送は重複しない。
- 原本条件や受信原文の変更、会社/役割/確認版違い、行追加中の取消と保護された同期拒否。
- 管理者作成1枠/2枠と複製2枠が、再取込後も同じ案件を指す。
- 旧IDのみ、旧新ID併存、別会社の同じcaseIdを区別する。
- 下書き・停止・予約公開・即時公開の指定を保持する。

修正前に管理者作成1枠/2枠の重複2条件を再現。ID修正後に新規1枠/2枠と複製の下書き自動公開3条件を再現し、最終修正後は15条件すべて成功しました。取込トランザクション57、リース12、受信作成50、受信公開46、管理者認証検査112、複製など業務API認証検査101、既存の実SDK業務往復9条件も成功。最初の取消試験は既存の同期拒否を成功返却と仮定していたため期待値を修正したもので、アプリ不具合の件数には含めません。

```sh
npm --prefix functions run build
node scripts/run-local-firestore-acceptance.mjs --suite creation-journey --java /path/to/java --jar /path/to/cloud-firestore-emulator.jar --evidence /path/to/new-evidence
```

実メール取得/送信、原本書込、実業務API呼出、worker配備、旧データ移行、停止解除は行いません。旧consumerの新規到着制御・旧実行終了・実配備範囲は別の未成立条件です。

読取処理はHTTPのsyncShiftSheetsReadOnlyと定期workerのsyncShiftSheetsScheduledで共用しています。作成APIだけ、またはHTTP読取だけを更新して全体が直ったとは扱いません。旧定期workerはこのPRで実配備しません。

旧ID照合はcompanyId/caseIdの等価条件だけを使い、手動索引を新設していません。一般仕様として等価条件の組合せは自動単一フィールド索引を利用できます（[Firebase公式の索引説明](https://firebase.google.com/docs/firestore/query-data/index-overview)）。実環境のフィールド索引免除などは未確認であり、将来の移行前確認が必要です。
