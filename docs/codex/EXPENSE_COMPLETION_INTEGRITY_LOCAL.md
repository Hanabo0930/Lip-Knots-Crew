# 経費の完了通知と現在状態の整合性

`updateExpenseReviewFromQueue`が古いイベント本文と検索時点の確認記録だけを使用していたため、確認の差替後の上書き、削除済案件の再作成、所属/担当変更後の金額反映、遅れて届いたblockedイベントによる完了の巻戻しを合成データで再現した。

最新のキュー・確認記録・案件を同じtransactionで読み、会社/案件/担当/現在queueIdと確認状態を照合する。下書きへの差替、削除、不一致、最新キューが処理中の状態では書き込まない。最新の確定状態だけを確認記録と案件へ原子的に反映し、他の経費付随フィールドは維持する。原本への書込方法や費用列、金額計算は変更しない。

実モジュールをTypeScriptから変換し、Firestore境界を合成データに差し替えた19ケースを`node scripts/test-expense-completion-integrity.mjs`で実行する。初期15ケース中11件の失敗を確認後に修正し、検索中の削除/担当変更と付随項目保持も追加した。ネットワーク・Sheets・実DBへ接続しない。SDKのtransaction再試行や実配信の試験ではない。

この修正はキュー処理結果の反映経路だけを対象とする。saveExpenseReviewDraft/completeExpenseReviewの保存競合、実表への書込、担当変更前に完了した実表の修復は別。今回のFunctionは既存配備許可外で、Hosting成功を稼働反映済みと扱わない。

## 下書き保存と確認完了の保存前検査（2026-09-09）

saveExpenseReviewDraft/completeExpenseReviewでも、最初の案件読取後に削除・所属変更・担当変更・経費変更・書込先変更が起きても古い状態のまま保存される問題を再現した。両APIは案件と既存確認記録をtransaction内で読み直し、最初に読んだ対象状態が維持されている場合にだけ保存する。別会社/別案件の確認記録は上書きしない。下書きのcreatedAtは初回値を保持し、完了時の版番号は安全な非負整数のみ許可する。

完了APIは以前、キューと確認記録の保存後にシートURL生成で失敗する場合があった。URLを保存前に検査し、URL不正時はキューを作らない。原本への接続や書込は行わず、既存の金額正規化・expected-value検査・明示的な既存値上書き確認の仕様は維持する。

既存19ケースを含む45ケース。入力用の有効な合成シート参照を用意した基準試験では21ケースの失敗を確認し、修正後はすべてPASS。証跡expense-save-baseline.json/expense-save-after.json。Firestore SDKのtransaction再試行を実行した検証ではなく、読取後の変更を合成境界で挿入する検証である。

保証範囲はAPI内の最初の読取から保存まで。画面を開いてからAPI呼出しまでの他管理者の変更、複数API呼出しの重複キュー、下書き同士の最終書込優先は解決していない。画面/APIをまたぐ版照合や受付IDによる重複防止は別途必要。両APIは未配備であり、実データを検証していない。
