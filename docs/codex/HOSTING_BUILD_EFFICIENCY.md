# STAGING Hostingの準備時間の短縮

StaffとAdminは別の出力先とTypeScript設定を持つため、Previewのビルドを同時実行します。両方の終了を待ち、どちらかが失敗したら配信前に停止します。容量検査とブラウザ検査は省きません。Promoteは検査済みの版を使い、再ビルドしません。

ブラウザ検査は既存のヘッドレス起動を継続し、未使用の通常Chromiumだけをダウンロード対象から外します。[Playwright公式の説明](https://playwright.dev/docs/browsers)に従い、channel指定なしのheadless用に--only-shellを使用します。将来channel指定や画面付きブラウザへ変える場合は取得方式も見直す必要があります。

実行ログのHOSTING_BUILD_DURATION_SECONDSでビルド時間を確認できます。並行実行はCPU/メモリを同時使用するため、常に一定割合で速くなる保証はありません。ローカルの比較は同じ設定・同じソースで両アプリの全成果物のSHA256を照合します。実環境はPreviewと公開後のブラウザ検査を別に通します。

## 再配信そのものの省略は未導入
ソースの変更ファイルだけでは、公開Firebase設定・VAPID設定・前回の配信失敗・外部からのサイト変更まで分かりません。省略するには、最後に成功した両サイトの配信版、現在の稼働版、ソースと公開設定の両方を照合した証拠が必要です。取得できない場合は従来の検査・配信経路を使う必要があります。

現在は全検査・固定環境・同SHA照合・保護環境・バックアップ・復旧条件を維持します。Functions、原本、GAS、実データ、IAM、Rules、Productionを変更する効率化ではありません。
