# 業務効率・速度を軸にした要件再点検（2026-09-05）

「最速」は単一の画面表示時間ではなく、正しい業務を完了するまでの操作数・待ち時間・再入力・問い合わせを最小化することとする。以下の数値は今回の開発目標案であり、達成済みの実測値や既存契約ではない。既存業務、会社分離、帳票整合、原本保持を性能のために弱めない。

## 性能の測り方と予算

比較には同じChromium版・ビルドSHA・fixture・画面幅・CPU/回線条件を記録する。初回と再訪を分離し、認証画面とログイン後ホームを混ぜない。ローカルは各条件20回の中央値/p95を記録し、小標本であることを付記する。実端末・実回線の受入結果とは別に保存する。

- 初回の主要情報表示：中程度の端末を想定したCPU 4倍低速・下り10Mbps/上り2Mbps/往復150msの試験条件でp95 2.5秒以内を目標案とする。認証メール待ち時間は別計測。
- 読込済み画面の切替・ローカル検索・入力応答：操作から結果の描画までp95 200ms以内を目標案とする。API応答待ちとは分離する。
- 操作受付：送信・更新を押した直後に処理中表示を出し、待ち時間を無反応にしない。失敗を成功表示で隠さない。
- データ量：Staffは過去0/300/1000件＋将来案件、Adminは100/1000/10000件の合成データで取得件数・DOM数・操作応答を測る。1000人同時利用を証明したとは扱わない。
- 転送：1/10/50MiB、1/3/20ファイルを分ける。50MiBは上り2Mbpsでも理論上約210秒を要するため、全転送を数秒以内とは定義しない。準備・実転送・Drive処理・状態確認を別計測する。
- 容量と通信：既存bundle予算を維持し、初期JS・API呼出数・重複要求を前後比較する。キャッシュの古さ・権限・会社が違えば再利用しない。
- 実負荷試験・メール送信・実データ書込はこの文書で新たに承認した扱いにしない。

## 実装照合で見つかった設計課題

1. **確定シフトの取得範囲**：Staff App.tsxのfetchMyJobsはdateKey昇順＋limit(300)。過去300件で上限に達すると将来案件が欠落し得る。今回、今日以降と過去を独立した各300件のクエリに分離し、過去件数で将来が押し出される問題を修正。過去履歴のカーソル段階取得と将来300件超の対応は次のP1として残す。日時境界、ソート安定性、会社・担当者条件、必要なインデックスを確認してから実装する。
2. **提出後の端末後片付け**：uploadSubmissionは転送成功後にclearDraftをawaitしてからファイル解除・Drive処理確認へ進む。端末削除だけが失敗すると送信全体が失敗したように見える可能性がある。クラウド受付済みIDの保持、再送抑止、残った下書きの扱いを一体で設計する。今回のtransaction abort修正だけで解決済みとはしない。
3. **管理者の一括処理**：画面整理で到達は改善済みだが、処理時間の基準データがない。未提出抽出→画像確認→経費→差戻しのfixtureを作り、操作数を測ってから追加機能を選ぶ。
4. **検証時間**：変更範囲のローカル検査を先に実行し、PRの必須CIを1回追跡する。失敗・追加変更がない限り全検査を繰り返さない。正しさを保ったまま待ち時間を減らす。

## 優先順位と判断

P0は誤った成功表示・データ混入・重複確定・操作不能の修正。P1は将来シフト欠落防止と業務導線の計測、初期読込と待ち時間の改善。P2は測定で根拠が得られた一括機能・検索拡張。既存のReact/Firebase/Sheets/Drive構成を、モデル変更や「最速」という言葉だけで全面置換しない。

機能追加は「誰の、どの作業を、何操作または何秒減らすか」「失敗時に何が残るか」「権限・同期・原本をどう守るか」「どの検査で合格にするか」の4点を満たしてから行う。画面の配色だけでデザイン完了とせず、情報の優先順・空/失敗/完了の区別・320px/文字拡大/キーボードを受入に含める。
