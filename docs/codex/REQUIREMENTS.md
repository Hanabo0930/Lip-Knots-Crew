# 業務要件と完成条件

## 今回の受入更新

Staffの業務優先ホーム、狭幅提出画面、画像復旧、転送失敗後の未開始分停止、会社・ユーザー別下書きについてローカルの回帰・ブラウザ検証が成功。必要機能は既存の提出フローを補強し、実送信を伴う新機能は増やしていない。

下書きの旧形式には所有者情報がないため、新形式へ自動移行しない。旧データは残るが復元対象外となる。提出済みファイルやサーバーデータは変更しない。

実スタッフのメール到達、50MBの実回線転送、管理者確認・再提出までの一往復、Admin画面の業務整理、運用受入は引き続き未完了。ローカル成功をそれらの受入へ置き換えない。


この文書は既存設計と会話を整理した現行の判断用一覧です。仕様の存在、コードの存在、STAGINGの実動作、利用者による受入を区別します。「完成率100%」をCI成功だけから算出しません。

## 目的と利用者

試食販売の案件募集、スタッフの確定シフト、事前準備、写真・報告書提出、再提出、管理者確認を一連の操作で扱い、転記と問い合わせを減らします。主な利用者はスマートフォン中心のスタッフと業務管理者です。過去の構想にある1,000人規模は設計目標であり、実測済みの能力ではありません。

## データと既存業務の約束

Google Sheetsは既存業務上の基準データ。Firestoreは一覧・状態・先着制御・通知・監査を担います。アップロード一時受信はCloud Storage、最終ファイルはGoogle Drive。スタッフ端末からSheetsへ直接書き込みません。

経費の既存列は交通費AK、8%費用AL、10%費用AM、ネットプリントAO、郵送APとして設計されています。実シートを確認せずに列・計算・GASを変更しません。競合する同期はexpected-value検査で止め、成功表示に置き換えません。

報告書と売場画像は別の提出種別です。再提出理由は複数指定でき、依頼状態は `open → submitted → completed`。古いファイルを削除せず比較と履歴を維持します。

通知の既存設計は22時〜7時停止、提出は翌平日11時期限などを含みます。詳細は [通知設計](../NOTIFICATION_SCHEDULE.md) を確認し、サーバー設定の実証と区別してください。

## 操作性・見た目・速度の評価基準

以下は今回整理した提案基準です。既存契約や未確認の利用者要望として扱わず、代表画面の測定と利用者確認で調整します。

- Staffは「何を・いつまでに・どこから行うか」が一画面で分かる。通常、待機、空、通信失敗、完了を区別する。
- 主要ボタンは指で押しやすく、キーボード操作と読み上げで用途が分かる。文字拡大、狭幅、長い店名でも操作を隠さない。
- 配色・ロゴは既存ブランドを維持し、本文のコントラストと情報の優先順位を見直す。
- Adminは日常業務から入れる構成を優先し、公開・SLO・技術診断などは必要なときに開く。権限判定は表示切替と別に維持する。
- 速度は同じ端末・回線・データ件数で、初回表示、操作応答、通信数、転送量を測る。HTTP 200やbundle上限だけで「高速」と断定しない。
- 画面操作は再描画前の連打も含めて重複しない。通信失敗後に再試行可能で、別案件・別セッションへ結果を混入させない。

## リリース判定

1. **ローカル品質**: 型・ビルド、関係する回帰検査、ブラウザの操作と画面確認。実行不能な検査は理由付きで残す。
2. **STAGING品質**: 同じSHAのCI、Preview、Promote、反映後検査、片付けが成功。
3. **業務受入**: 登録スタッフがログイン→シフト確認→提出→管理者確認→再提出完了を行える。メール・ファイル・一覧・Sheetsが一致する。
4. **運用受入**: 3〜5名のパイロット、実GAS監査、実データ照合、通知到達、権限ケース、監視、業務データ復元、規約確認。
5. **Production判断**: 上記とは別の明示承認が必要。この作業では実施しない。
