# 行作成キューの遅延イベント・再試行競合

遅れて届いた pending イベントが、完了・実行中・停止済みの依頼を paused_global に戻す場合がありました。再試行の検索と更新の間に完了・予約変更・削除された依頼も、古い検索結果で pending に戻していました。

実行権取得時にトランザクションで現在の依頼を読み、pending の場合だけ運用状態を確認して停止または実行中へ移します。処理対象の会社と案件も取得時の内容を使います。再試行は検索時刻を固定し、各依頼の現在の状態・期限・存在を再確認してから pending にします。環境の停止判定と再試行上限50件は維持します。

`test-local-row-queue.mjs` は隔離 Firestore Emulator と実 SDK で、遅延・重複配送、状態変更、削除、会社・案件変更、再試行期限変更、50件上限の22条件を確認します。運用状態取得だけを合成境界に置換し、Sheets接続を禁止します。修正前は22条件中18条件で問題を再現し、修正後は22条件すべて成功しました。既存の停止試験36条件は TypeScript とコンパイル後 JavaScript の両方を確認します。

```sh
npm --prefix functions run build
node scripts/test-sheet-row-creation-pause.mjs
node scripts/run-local-firestore-acceptance.mjs --suite row-queue --java /path/to/java --jar /path/to/cloud-firestore-emulator.jar --evidence /path/to/evidence
```

この修正は行作成中の外部書込と業務文書更新を一体で原子化するものではありません。運用設定の取得も依頼のトランザクションとは独立した読取です。実環境での新規到着停止・旧実行終了は別途確認が必要です。worker の配備、実キューの再実行、停止解除、実表への書込はこの検証に含みません。

## 失敗処理の業務文書保護

失敗処理も、実行権を得た会社・グループ・案件一覧・試行回数と現在の processing 依頼が一致する場合だけ反映します。依頼と関連文書をトランザクションで読み、存在する同じ会社の案件・グループだけを更新します。案件はグループ一致も必須です。削除済み文書の復活、別会社・別グループへの失敗反映、終了後や別試行への巻戻しを防ぎます。

追加15条件の修正前試験で14失敗を再現し、修正後は既存22条件と合わせ37条件成功。さらに初回・途中・上限到達のシステム失敗3条件を加え、再試行期限と5回上限を含む40条件すべてが成功しました。これらは実SDKと隔離DBの試験で、実環境の業務データ被害を観測したものではありません。成功時の外部書込・業務文書反映の競合は別の確認対象です。

## 成功反映と取消の保護

すでに行作成済み、重複完了の短絡経路でも現在の試行を確認します。行追加後の完了反映は依頼・ロック・会社・グループ・案件ID・入力値・書込設定をトランザクションで再照合し、現在の取消・担当・募集変更を保ちます。外部APIはこのトランザクションの中から呼びません。

業務文書や設定が変わった場合は、既存の案件ID照合に加えロックの所有者と期限を確認してから追加行を取り消します。実行権を失った場合、照合できない場合、自動取消が無効の場合、完了保存の成否が不明な場合は原本を推測で削除せず要確認記録を残します。完了保存の応答喪失後も保存済みの業務状態を巻き戻しません。

`test-local-row-success.mjs` の48条件では、隔離Firestore実SDKと合成Sheets応答を使い、短絡経路の旧試行、従来/受信案件の取消・担当・募集変更、削除・会社変更・入力変更、ロック喪失、取消の成功/照合不成立/読取エラー/無効化、完了保存の応答喪失を検証します。既存の行作成40条件、停止36条件、受信募集46条件も維持します。

この検証は実worker配備や原本操作を行いません。SheetsとFirestoreの分散トランザクションを実現するものではなく、挿入API自体の応答喪失は後段で別に保護します。実環境の旧実行終了は引き続き別の確認対象です。

## 挿入APIの応答喪失

行追加APIがエラーを返した場合、適用済みか未適用かをクライアントだけで断定せず、予定範囲を `plannedInsertion`、結果を `insertionOutcome: unknown` として要確認にします。確認済みの追加範囲 `inserted` と区別し、自動再試行・推測での行削除を行いません。送信前の列設定不足は従来どおり blocked です。

合成環境で修正前に3条件の失敗（応答喪失・送信失敗・再試行で二重追加）を再現。成功試験は51条件へ拡張し、応答喪失後の同じイベントの再配信で追加を増やさないことも確認し、51条件すべて成功しました。実環境のAPI実行・業務記録の再試行は行いません。
