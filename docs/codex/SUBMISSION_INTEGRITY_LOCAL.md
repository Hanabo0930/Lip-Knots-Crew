# 提出から再提出完了までの整合性検証

2026-09-08。提出作成→Drive転送→再提出依頼→差替→比較→管理者完了と、その途中失敗・並行実行を一括で検証した。実クラウド/実業務データは使用していない。

## 修正した挙動
- 転送前に提出とファイルの会社・UID・案件・スタッフ・種別・再提出先を照合し、同じtransactionで現在の会社/担当者/設定を確認する。転送中に担当者が変わった場合も、完了集計と案件完了で再確認して誤反映を停止する。
- 再提出の処理開始時に、その依頼を最初の提出IDへtransactionで紐付ける。別の提出セッションは転送前に停止する。同じ提出の複数ファイルと同一イベントの再実行は受け入れる。
- 再提出依頼へのファイル追加・提出済み化・管理者完了は存在と対応する提出をtransactionで検証する。消えた依頼を再作成せず、完了済み依頼のファイルを後から差し替えない。管理者完了の再送は成功済みの結果を維持する。
- 親/ファイル消失時にエラー処理や転送チェックポイントが文書を再作成しない。矛盾するカウンタ、未転送の親、別案件、担当変更・案件消失を成功扱いして一時ファイルを削除しない。
- 古い転送の復旧が後着しても、初回は最も早い時刻、最新は最も遅い時刻を保持する。追加提出で初回遅延のキュー表示が「提出済」に変わる不整合を修正する。
- 旧形式の完了画像を元に管理者が再提出を依頼する操作は維持する。旧ファイルの自動再加算を許可する変更ではない。

## 検証
`scripts/test-submission-lifecycle.mjs`を正規CIの既存ステップで継続実行する。元の30ケースに31ケースを追加し、合計61ケースが成功。

修正前に再現したのは、所属情報8経路、消失した再提出依頼の復活、別セッションによる上書き、元提出の会社不一致、転送中担当変更、案件消失、未完了親/別案件の完了、初回遅延消失、時系列逆転、削除済み親/ファイル復活、完了済み数への再加算。正常系は同じ提出の並行複数ファイル、管理者完了再送、旧形式元画像の再提出依頼も検証する。

実際のTypeScriptモジュール全体を読み、SDK・Storage・Driveだけを合成境界へ差し替える。読取版番号を用いたtransaction再試行を模擬する。型検査は別途Functionsのtscビルドで確認する。実Firestore並行transaction、実イベント配信、実Drive、実ログイン/ブラウザーからの送信を受入済みとは扱わない。

## 配備と回復上の制約
Functionsは未配備。対象はfinalizeStagedUploadと共有モジュール、createResubmissionRequest/completeResubmissionRequest。後者2つは既存無人配備の許可外であり、勝手に許可リストへ追加しない。Hosting成功をこのサーバー修正の稼働証拠としない。

最初に処理を開始した再提出IDの予約はエラー時も保持し、その提出の再実行で回復する。別提出への予約の移し替え、実データ修復、旧版と新しい予約データの互換性を含むクラウド受入は別途必要。転送途中に所属が変わった場合、コピー済みのDriveファイルとチェックポイントを残し、無条件削除や新担当者への付替えをしない。事前検査で拒否した不整合はイベントエラーとなり、UIのwaiting_uploadがそのままの場合もある。専用の管理者修復操作は追加していない。

取消後の写真/経費受付の未確定方針は今回変更しない。原本への実書戻し、実DB/Storage/Drive操作、GAS、メール/通知、Rules/IAM、Productionは実行していない。
